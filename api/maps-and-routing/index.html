Maps & Routing API

The v4 API serves everything a map client needs from the Resgrid server: the department's base map as a MapLibre style, static map images, routes and drive times from the installation's routing provider, live navigation ETAs, route plan routing, destination rankings and suggestions, and offline map packs. No client calls Mapbox, Google, Valhalla or OSRM directly, and no routing or geocoding token ever leaves the server. For what users see, see Mapping, Destinations, Routes and Department Settings → Mapping; for setting up providers on your own server, see Maps & Routing (self-hosted).

Configuration fields​

GET /api/v4/Config/GetConfig returns these fields beside the existing map fields, which keep their meaning for older app builds:

FieldDescription
MapRenderermaplibre when the fields below are filled
MapLibreStyleUrlDay, MapLibreStyleUrlNightSigned Mapping/GetStyle URLs for the department's day and night base map
MapRasterTileUrlRaster XYZ tiles ({z}/{x}/{y}) for pixel-space maps and fallbacks
StaticMapUrlTemplateSigned Mapping/GetStaticMap URL with the placeholders {lat} {lon} {zoom} {width} {height} {scale} {scheme}
TrafficAvailable, TrafficTileUrl, TrafficRefreshSecondsLive traffic vector tiles (Mapbox Traffic v1, public token included) and how often to reload them
TrafficRasterTileUrlThe department's own traffic image tiles ({z}/{x}/{y}, for example TomTom flow), set in Mapping Settings. When it is set, TrafficAvailable is false and TrafficTileUrl is empty, so clients that only draw vector traffic show none instead of misreading the images
RoutingProvider, RoutingSupportsTraffic, RoutingSupportsIncidents, RoutingSupportsVoiceWhat the installation's routing can do
NavigationAvailableIn-app navigation may be offered: the routing provider is Valhalla or Mapbox, navigation is enabled on the installation and the department has Navigation.InApp
OfflineMapsAvailable, OfflineManifestUrlOffline packs are on for the department (Maps.Offline), and the signed manifest URL to call exactly as given
AmbientCacheMaxBytesThe tile cache budget a native client should set

Signed URLs​

Map sources in native and web map libraries cannot send an Authorization header, so map resources accept a signature instead of a bearer token: d (department), e (expiry, Unix seconds) and sig (HMAC) query parameters. The signature covers the department, the kind of resource and the expiry, not the other query values, so a signed template stays valid after its placeholders are filled. URLs live SignedMapUrlTtlHours (24 hours by default); refresh them by fetching the configuration again. An expired or wrong signature answers 401, or 410 for offline downloads so the client knows to fetch a new manifest.

POST /api/v4/Mapping/SignMapResourceUrls (bearer, Call_View) signs custom map tile and image URLs and indoor floor image URLs of the caller's department; template URLs ({z}/{x}/{y}) stay valid after signing, and URLs for other resources or other departments come back null.

Styles and static maps​

EndpointMethodAuthDescription
/api/v4/Mapping/GetStyle?key=&variant=day\|nightGETBearer or signedThe department's base map as MapLibre style JSON: a Mapbox style with every mapbox:// URL rewritten, the installation's self-hosted style, or a raster style. key is the app surface (empty for the website)
/api/v4/Mapping/GetStaticMap?lat&lon&zoom&width&height&scale&scheme[&marker=0][&style=]GETSignedA PNG/JPEG map image. zoom is a MapLibre zoom, scale 1 or 2, scheme day or night; a centre pin is drawn unless marker=0. style (a MapStyleTypes value) previews that style instead of the department's own, as the Mapping Settings page does
/api/v4/Mapping/GetCustomMapMercatorTile/{layerId}/{z}/{x}/{y}GETBearer or signedA georeferenced custom map layer as Web Mercator tiles; 204 outside the layer, 404 for a layer with no geographic position

GetStaticMap uses Mapbox Static Images on a Mapbox installation; on a self-hosted one it uses the style server's static images (TileServer GL …/styles/{id}/static/…) when the style comes from one, else it stitches the installation's raster tiles.

Every request goes to the installation's routing provider, then its fallback provider, and finally to a straight-line estimate, so a route always comes back.

ReportNavigationProgress​

Sent by an app navigating a unit: on start, reroute, arrival and end, and at most every 15 seconds while navigating. Dispatch and Big Board show the ETA live.

FieldDescription
UnitIdThe navigating unit
CallId or RouteInstanceId (+ RouteInstanceStopId)Where it is going
State0 Started, 1 Progress, 2 Rerouted, 3 Arrived, 4 Ended. Arrived and Ended clear the unit's live ETA, as does the unit setting a status such as On Scene or Available
EtaUtc, RemainingSeconds, RemainingMetersThe estimate; without EtaUtc the server uses now + RemainingSeconds
IsTrafficAware, ProviderHow the estimate was made

GetActiveNavigations lists each navigation the caller may see (the call, and the unit's location) with the same fields, ReportedOn, and IsStale after 60 seconds without a report. A change is pushed on the eventing hub as unitNavigationUpdated, carrying ids only; read the ETA from GetActiveNavigations.

Travel modes​

GetCallRoute with a unitId follows the unit's travel mode: a walking unit is routed on foot (profile 3) and a cycling unit by bike (4), without vehicle limits; driving and air units get the road route with their vehicle size and weight, as before. GetRoute uses the Profile you send.

GET /api/v4/Dispatch/GetNearestUnits (the nearest-units board) measures each unit by its travel mode. Each row of Data.Units also has:

FieldDescription
TravelMode0 Driving, 1 Cycling, 2 Walking, 3 Air
EtaSourceGains 3 Direct: an air unit's straight-line time at its air speed, not an estimate (1 Estimated and 2 Road as before)
RoadClosureDelaySecondsSeconds active road closures added to the routed time; 0 when none
RoadClosuresNames of the active road closures the unit's route was measured against (avoided, slowed by or crossing)

Personnel rows are always measured as driving.

Road closures​

The department's road closures are drawn and managed on the website. The routing endpoints apply them; apps can read them to draw on their maps.

EndpointMethodAuthDescription
/api/v4/RoadClosures/GetRoadClosures[?activeOnly=true]GETBearer, Call_ViewThe closures in effect now and those still to come; activeOnly=true returns only those in effect now. Ended and switched-off closures are left out

Each item of Data:

FieldDescription
RoadClosureId, NameThe closure
ClosureType0 Other, 1 Event, 2 Road works, 3 Incident, 4 Police, 5 Weather, 6 Hazard on the road, 7 Bridge, tunnel or crossing
Severity0 Full (no through traffic), 1 Partial (slowed)
SpeedPercentSpeed inside the closure, as a percentage of normal
AppliesToFlags of the traffic it stops: 1 vehicles, 2 bicycles, 4 pedestrians
State0 In effect, 1 Scheduled
IsEnabledSwitched on (always true in this list)
GeometryThe closed areas and road lines as a GeoJSON FeatureCollection of Polygons and LineStrings
WindowsClosure times in UTC: StartsOn and EndsOn (null: until further notice). Empty: in effect until switched off
Reason, ClosedBy, Authority, ContactName, ContactDetails, NotesThe details entered on the website
UpdatedOnLast change, UTC

GetRoute and GetCallRoute apply the department's closures that are switched on and in effect at the time of the request, for the route's profile: pedestrian closures for 3 Walking, bicycle closures for 4 Cycling, vehicle closures for the driving profiles. Full closures near the route are avoided as far as the provider can (Valhalla avoids drawn areas and road lines; Mapbox driving profiles avoid points along closed roads and re-route up to twice out of a closed area; Google and OSRM cannot avoid them), and a route that still crosses one is charged the closure's detour time. Partial closures, and a full closure the route starts or ends in, slow the time spent inside them to the closure's SpeedPercent. DurationSeconds includes all of this, RoadClosureDelaySeconds says how much of it the closures added, and RoadClosures lists them. Route plans do not apply closures.

Routes on calls​

A call can carry a route plan (RoutePlanId on SaveCall / EditCall), which the unit working it runs (Routes on calls). A plan a call can follow starts and ends at its station or explicit point, else at its first and last stop; GetCallRoutePlans returns both ends and whether each is a stop (StartIsStop, EndIsStop).

A run started with StartCallRoute is linked to the call (CallId). When its plan starts at a station or point, GetInstanceDirections with a position and includeStart=true leads from the unit to that start before the first stop, until the run records StartReachedOn (by ReachRouteStart, or by the unit asking for directions within the plan's geofence radius of the start, default 100 m) or a stop has been worked. That leading leg and the waypoint it ends at have IsRouteStart: true; the waypoint has StopOrder 0 and no stop ids. Without includeStart, or for ordinary runs, the directions are as before.

"Or a call's run": for a run linked to a call, members who may see the call can read it and preview its active plan without Route_View, and those who may also see the unit can work it (start, check in and out, skip, notes, pause, resume, end, cancel, deviations, reaching the start) without Route_Update. See API information → Call locations, destinations and routes for the call fields and the results.

MapboxRouteGeometry on a plan now holds the generated route as a GeoJSON LineString string, and MapboxRouteProfile keeps its old values (driving, driving-traffic, walking, cycling; Truck is driving).

Destinations​

A department's destinations are its POIs whose type has IsDestination. What they offer, whether they can take anyone now, and which one suits a call are described in Destinations; these endpoints serve them to the apps.

EndpointMethodAuthDescription
/api/v4/Mapping/GetPoiCapabilitiesGETBearer, Department_ViewThe department's capabilities (PoiCapabilityId, Name, Sort), in its order
/api/v4/Mapping/GetPois?poiTypeId=&destinationOnly=, GetPoi/{poiId}GETBearer, Department_ViewPOIs with CapabilityIds, Capabilities (names), AvailabilityStatus (0 Open, 1 Limited, 2 Diversion, 3 Closed; an expired report reads 0), UnavailableCapabilityIds, AvailabilityNote, AvailabilitySetOnUtc, AvailabilityExpiresOnUtc
/api/v4/Mapping/GetNearestDestinations?latitude&longitude[&capabilityId][&unitId][&take=10]GETBearer, Department_ViewDestinations nearest a point, optionally only those offering one capability: those that can provide it first, diversion next, closed or with the capability down last. The 5 closest that can take the patient are routed (TravelSeconds, TravelDistanceMeters; -1 when not routed), the rest ranked by DistanceMeters (straight line). unitId applies the unit's travel mode and vehicle limits; a unit the caller cannot see is ignored. take 1–50
/api/v4/Mapping/GetSuggestedDestinations?latitude&longitude[&type][&priority][&callId][&unitId][&take=10]GETBearer, Department_ViewThe destination suggestions for a call (type = call type name, priority = the call's Priority value; both taken from callId when left out) and, with unitId, the unit travelling for it (its type's rules apply). Returns Mode (0 Off: nothing is returned or routed), PreferredWithinMinutes, SuggestedPoiId (the best destination that meets the requirements and is not closed, or null), Requirements (PoiTypeIds, RequiredCapabilityIds, PreferredCapabilityIds, Rules and SetAsideRules with Reason TypesRemoved / TypeConflict) and Destinations ranked best first, each with Poi, the distances and travel time, CanProvide, Status, MeetsRequirements, MissingCapabilityIds, PreferredCapabilityIds and Tier (0 ready, 1 diversion, 2 lacking, 3 closed)
/api/v4/Mapping/GetDestinationRulesGETBearer, Department_ViewRead only: the suggestions Mode and PreferredWithinMinutes, and every destination rule most specific first, with its ids, the names they refer to and MissingReferenceCount (ids naming something deleted)
/api/v4/Mapping/SetPoiAvailabilityPOSTBearer, Call_Create{ "PoiId": 214, "Status": 2, "UnavailableCapabilityIds": ["…"], "Note": "ED capacity overload", "ExpiresInMinutes": 240 }. Status 0 clears the report; ExpiresInMinutes null or 0 lasts until changed, at most 7 days. Returns the POI after the change; 400 for a POI that is not one of the department's destinations

GET Config/GetConfig carries the department's DestinationSuggestionMode (0 Off, 1 Suggest, 2 Suggest and fill) and TransportDestinationChecks, so an app knows whether to ask for suggestions at all. Each suggestion looks up drive times: ask once the call has a location, and again only when its type, priority or location changes, or when the unit it is asked for changes — unitId decides which rules apply and whose travel mode is routed, so a unit picked after the first request needs a fresh one.

Offline map packs​

The offline manifest lists everything an app downloads for use without a network (see Offline maps). Call the signed OfflineManifestUrl from the configuration exactly as given; every URL in the manifest is signed and on the same origin.

EndpointMethodAuthDescription
/api/v4/Mapping/GetOfflineManifestGETBearer or signedBase map cells over the department's response area, custom map rasters, indoor and custom map images, the department data bundle, sprite and offline styles, each with a size, SHA-256 and download URL
/api/v4/Mapping/GetOfflinePack/{packId}[?file=]GETBearer or signedA built pack (PMTiles), or one sprite file. Supports HTTP Range; the ETag is the SHA-256
/api/v4/Mapping/GetOfflineDepartmentDataGETBearer or signedThe department data bundle: gzip JSON of GeoJSON collections (layers, POIs, stations, hydrants …)
/api/v4/Mapping/GetOfflineAsset/{name}GETBearer or signedAn offline style or glyph archive (day.json, night.json, glyphs.zip)
/api/v4/Mapping/EstimateResponseAreaPOSTBearer, Department_View{ "GeoJson": "…" }: the base map download size of a response area against the installation's limit; an empty area measures the default circle

Packs are built in the background by the worker, the first time a manifest asks for them. Each pack carries a Status; one not built yet has no download until it is, so fetch the manifest again later.

Outside the response area the manifest also lists incident packs (Kind 1: base map cells around each active call) and route corridor packs (Kind 2: cells along each active route plan). These carry CallIds (the calls whose radius touches the cell) and RoutePlanIds (the route plans whose corridor touches it), so a device downloads only the packs for the calls and routes it works on. One cell can be near several calls and routes at once, so both are lists, and a cell can list route plans whatever its Kind. Other packs return null for both.
